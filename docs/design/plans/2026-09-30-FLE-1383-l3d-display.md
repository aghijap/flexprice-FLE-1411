# L3-D — Display & API surface — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL at execution: superpowers:executing-plans, TDD each step. Scoping plan — confirm the invoice response/webhook builders and PDF/portal templates before implementing.

**Goal:** Make the frozen conversion visible everywhere a customer or integration reads an invoice: API/webhooks expose `fx_conversion` + line originals, the PDF and portal show "converted from …", drafts show a billing-currency estimate, and invoices are filterable by the original charge currency.

**Spec:** ERD §9.3 (and the "where the frozen rate is visible" table).

**Depends on:** L3-A (`fx_conversion`, line originals exist and are populated). Stacked on `feat/FLE-1383-l3c-wallets-refunds` (or earlier — rebase as needed). Lowest-risk PR; user-facing polish.

## Global Constraints

- Read-only surface — no new writes, no conversion logic here (all of that is L3-A/C).
- `billing_currency_estimate` is **calculated on read, never saved** (drafts/previews only).
- Handle the **tax line with no `original_amount`** gracefully (it's added post-conversion) — show only the billing amount for lines without an original (#7).

## Review Focus

- `resolvable: false` in the draft estimate tells the dashboard the draft will fail to finalize (missing rate) — surface it, don't hide it.
- Webhooks wrap the invoice response, so exposing `fx_conversion` on the invoice DTO should flow to webhooks with **no builder change** — verify.
- PDF/portal must render a line **without** an original (tax line) as just the billing amount, and lines **with** an original as "₹X (from $Y at rate)".
- `charge_currency` filter matches the **original** currency; the existing `currency` filter matches the billing currency — keep both.

## File Structure

- `internal/api/dto/invoice.go` (or the invoice response builder) — ensure `fx_conversion` + line `original_currency`/`original_amount` are in the invoice response (likely automatic via the domain model; verify) and thus in webhooks.
- Invoice list filter — add `charge_currency` (filters on line `original_currency`).
- Draft/preview response — `billing_currency_estimate` `{ currency, rate, total, resolvable }`, computed on read via `FXRateService.ResolveRate`.
- PDF template + customer portal — "converted from" text on totals and per line.
- `make swagger` + `make sdk-all` (SDK regen; runs in CI if no local Speakeasy key).

## Tasks

### Task 1 — API + webhook exposure
Confirm/extend the invoice response so `fx_conversion` and line originals serialize; add a test asserting a converted invoice's JSON matches §9.3 (nulls on non-converted). Verify webhook payload includes them (no builder change).

### Task 2 — `charge_currency` list filter
Add the filter on line `original_currency`; keep the existing `currency` (billing) filter. Test both.

### Task 3 — `billing_currency_estimate` on drafts/previews
Compute on read (resolve rate, project total); include `resolvable` (false when no rate). Shown only when billing currency differs from the draft currency. Never persisted. Test resolvable true/false.

### Task 4 — PDF + portal
Render "₹8,300.00 (converted from $100.00 at 83.00)" on totals and per line that has an original; plain billing amount for lines without one (tax line). Snapshot/template test.

### Task 5 — Swagger + SDK regen
`make swagger`; commit the additive spec; `make sdk-all` (or leave to CI).
